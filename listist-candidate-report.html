diabeteshelper · evaluation · 2026-10-06 · commit 16173e1 · no code changed

A small app with one real option list: the logbook "activity". Listist would help a little here, not a lot.

The repository is a single-screen-stack Flutter app (about 2,300 lines of Dart in lib/) with one local SQLite table and no backend, API contract, migrations, i18n or agents. I found 5 closed or implied vocabularies. Only one of them, the logbook activity list (Breakfast, Lunch, Dinner, Walking, Cycling), is used across 3 layers: the picker, free-text storage and the CSV export. Its copies disagree in one verified way: the picker suggests five values, but every entry path stores any free text, and the stored value is the display label. No live bug comes from drift. I did find one unrelated live bug: the logbook only lists entries whose carbs value is exactly "2". The most useful place for Listist is the activity list, plus a units list if blood-glucose units are ever made explicit.

Sources: the Listist skill and handbook (/api/v1/begin), both fetched live on 2026-10-06. I read every Dart file under lib/, plus pubspec.yaml, README.md, the iOS Info.plist, the CI workflow and the git history (git log -S). I ran the grep patterns from the skill's search reference for each layer.

Listist in this codebase's terms

Keep each list once

The activity list is written once in code, at lib/pages/logbook.dart:107. It was also restated in the README until commit 26a53c0, and that copy differed (it added "a custom one", and a planned preset list added Snack). As a Listist list it might be org:diabeteshelper:logbook.activity@v1.

Pin immutable versions

The Client table stores only activity TEXT (lib/database/database.dart:34). It has no list id or version, so rows in old CSV exports can't be traced back to the list version they came from.

Values are identity

The display label is the stored value. DropDownField writes the label it shows (logbook.dart:290, :525), and the export writes that label as is (database.dart:51-59).

Retire, never delete

No value has been renamed or removed in code yet. The README's planned Snack preset was dropped along with the rest of the roadmap text (26a53c0). Nothing references it now.

People curate, agents read

None found. There are no agents, prompts or LLM calls in the repository.

Never auto-upgrade a pin

Nothing reads a list from a remote "latest". The food search calls Edamam's food-database/v2 (lib/pages/home.dart:50). The API version is pinned in the URL path, but the response vocabulary (food category, nutrient codes) is not.

Look up raw strings

strict: false on both activity pickers (logbook.dart:292, :527) accepts any typed text with no normalisation. A lookup against the activity list would map "breakfast" or "brekkie" to one value.

Do not invent values

The five activities are typed inline (logbook.dart:107-109), and the "custom" option is just free text. The nutrient key CHOCDF is typed inline in two places (lib/models/foodmodel.dart:19, :33).

1. Logbook activity / entry type

product vocabulary
Copies

Code: lib/pages/logbook.dart:107-109 (activit), used by the pickers at :290 and :525. Storage: lib/database/database.dart:34, lib/models/logbookmodel.dart toMap/fromMap. Export: database.dart:51-59 (CSV). Unused free-text form: lib/pages/add_editclient.dart:80. Docs: README until 26a53c0.

Drift

The list has 5 values, but every write path accepts arbitrary text (verified). The old README said "options like Breakfast, Lunch, Dinner, Walking, Cycling and a custom one", and planned presets "Breakfast, Lunch, Dinner, Snack". Snack was never added to code (verified in history). Meals and exercise share one field.

What Listist changes

The values would live in one place with stable ids (for example breakfast), separate from locale labels. Stored rows and exports would carry listId@version. Typed text would be resolved with the lookup endpoint instead of being stored raw. Values would be retired, not removed, if the meal/exercise split changes.

Existing public list

Not checked. The Listist search calls were blocked in this session (see Method and caveats).

Proposed id

org:diabeteshelper:logbook.activity

Rough cost

Small to medium. Existing rows store labels or free text, so the history would need a one-time mapping. The app has no server to cache a pinned list, so it would ship a bundled fallback.

2. Measurement units

reference data
Copies

"Carbs (g)" is a column heading (logbook.dart:203). Per-100 g arithmetic is in lib/fooddetail.dart:46. "BG level" (logbook.dart:213) and "Insulin" (:233) have no unit. The bg, insulin and carbs columns are all TEXT (database.dart:35-37).

Drift

The data is free text in a place where a closed list exists in the real world: blood glucose is recorded in either mmol/L or mg/dL, and the app records neither. This is a gap, not a copy disagreement.

What Listist changes

A pinned unit list would give each stored reading an explicit unit value, so exports become unambiguous.

Existing public list

Not checked (blocked). A public units list (for example a UCUM subset) is worth checking before anyone proposes a new one.

Proposed id

public units list, if one exists; else org:diabeteshelper:units.glucose

Rough cost

Medium. Adds a stored field per reading, and existing readings have an unknown unit.

Agents and prompts

None found. The repository has no LLM calls, prompt templates, tool definitions or agent configuration. The only AI-adjacent plan was in the old README: a preset-based insulin calculator ("select their preset … enter their carb intake, the system will output how many units they need"), removed in 26a53c0. If that feature returns, the preset list it uses would need validated, stable values, and the activity list would be the natural source.

Where not to use Listist

  • The log entries themselves (Client rows: carbs, BG, insulin, notes, datetime). These are a person's own health records, not a vocabulary.
  • The log field names (activity, insulin, carbs, bg, datetime, notes), repeated across database.dart:33-39, logbookmodel.dart and the column headings at logbook.dart:203-244. This is schema, even though the labels drift ("bg" / bglocouse / "BG level").
  • Food search results from Edamam (home.dart:72). These are rows from an external search, not options.
  • Bottom navigation tabs ("Search", "Resources", "Log book" in lib/main.dart). These are UI routes.
  • Ad unit identifiers in home.dart and respage.dart. These are configuration, not vocabulary.

Decisions needed

  • Fix the logbook filter (search("carbs", "2"), logbook.dart:261) now, separately from any Listist work?
  • Is "activity" one list or two (meal vs exercise)? Should Snack and a deliberate "Other" value be added, and should free text still be allowed?
  • Which blood-glucose unit does the app mean, and should each reading store its unit?
  • Is a single offline app worth a network-backed list at all, or is the activity list enough as a pinned, bundled copy?
  • Security, outside Listist: the food-API credentials are hard-coded in source (lib/pages/home.dart:50 and :61; values redacted here), although the README says users must supply their own. Should they be revoked and moved out of the repository?
  • Should the Listist catalogue search (step 9) be run with permission, so the reference-data cards can name existing public lists?
